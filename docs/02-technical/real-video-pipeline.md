# Real Video Pipeline

Replaces the synthetic `test_video.mp4` with curated real driving footage.

---

## Critical decision: training data ≠ HCI study stimuli

These two roles need **different** datasets:

| Role | Dataset | Why |
|---|---|---|
| **Training** the self-supervised depth model | KITTI raw sequences | Calibrated cameras, LiDAR ground-truth (lets you compute AbsRel / RMSE for the thesis), standard benchmark in self-supervised depth literature, ~50 hours of varied driving |
| **HCI study stimuli** (15 trial clips) | BDD100K subset OR curated YouTube dashcam compilations | Lots of critical events (pedestrian dashes, near-misses, sudden brake). KITTI is mostly uneventful Karlsruhe driving — bad reaction-time material. |

This separation also strengthens the thesis story: "Trained on KITTI (standard benchmark) and evaluated on a separate set of dashcam scenarios (ecological validity)."

## HCI Stimuli — Goal

15–20 short scenarios, each 5–10 seconds, with a known critical event at a known timestamp.

Required mix:
- **6 critical** events (pedestrian / brake-light / cyclist / lane intrusion)
- **6 warning-level** events (vehicle approaching but not yet dangerous)
- **3 safe** clips (no event — control to detect false alarms)

---

## Curation criteria (per clip)

| Property | Requirement |
|---|---|
| Duration | 5–10 s |
| Resolution | ≥ 720p |
| Front-facing | Dashboard mounted, not 360° |
| Daylight | Mostly daytime (consistent lighting for thesis controllability) |
| Critical-event timestamp | Note when the danger first becomes visible |

---

## Naming convention

`<id>_<event_type>_<expected_alert>.mp4`

Examples:
- `01_pedestrian_critical.mp4`
- `02_pedestrian_warning.mp4`
- `03_brake_lights_critical.mp4`
- `04_cyclist_warning.mp4`
- `05_lane_intrusion_critical.mp4`
- `06_safe_highway.mp4`

---

## scenarios.csv format

| Column | Type | Description |
|---|---|---|
| `id` | string | Matches filename prefix (e.g. "01") |
| `filename` | string | e.g. `01_pedestrian_critical.mp4` |
| `event_type` | enum | pedestrian / brake_lights / cyclist / lane_intrusion / safe |
| `expected_alert_level` | enum | CRITICAL / WARNING / CAUTION / SAFE |
| `event_start_ms` | int | When the danger first becomes visible (0 for SAFE clips) |
| `duration_ms` | int | Clip length |
| `source` | string | BDD100K / KITTI / YouTube URL |
| `license` | string | CC-BY / fair-use / academic-only |
| `notes` | string | Any clip-specific quirks |

## Workflow — YouTube approach (fastest for week 1)

```bash
# Install tools (one-time)
brew install yt-dlp ffmpeg

# 1. Find a dashcam compilation video on YouTube
#    Search: "dashcam compilation 1080p 2024" or "near miss dashcam"

# 2. Download (saves to data/raw_downloads/)
yt-dlp -f "best[height<=1080]" -o "data/raw_downloads/source_%(id)s.mp4" "<youtube-url>"

# 3. Find the critical events by scrubbing — note start times
#    e.g. pedestrian appears at 02:14, lasts 8 seconds

# 4. Trim into a scenario clip
ffmpeg -ss 00:02:14 -i data/raw_downloads/source_XYZ.mp4 -t 8 \
       -c:v libx264 -preset fast -crf 23 -an \
       data/scenarios/01_pedestrian_critical.mp4
#    -an drops audio (we don't need it; alert audio is generated by the app)
#    -c:v libx264 re-encodes to ensure clean cuts (vs -c copy which keyframe-snaps)

# 5. Add row to scenarios.csv
```

## Workflow — BDD100K approach (more rigorous, slower)

```bash
# 1. Register at https://www.vis.xyz/bdd100k/ (academic email helps)
# 2. Download videos_train_00.zip (sample subset, ~5 GB)
# 3. unzip and pick 20 candidate clips
# 4. Trim with ffmpeg as above
```

BDD100K is preferred for the thesis writeup ("citable dataset") but slower to start with.

## Quality check before locking in scenarios

For each clip, run DepthGuard with DepthPro and verify:
- Alert fires within ±500 ms of `event_start_ms`
- No false-positive CRITICAL alerts on safe stretches
- Depth map looks plausible (vehicles / pedestrians stand out)

If a clip doesn't behave well, retune ROI in `src/core/alert_system.py` or replace the clip.

A future helper script `scripts/validate_scenarios.py` should automate this — runs DepthGuard pipeline over each clip and reports timestamp mismatches.

## Code changes needed in DepthGuard

To go from "load one video" to "run a participant playlist":

1. **Scenario loader** — replace single `Load Video` with `Load Playlist` button that reads `scenarios.csv`
2. **Trial counter UI** — show "Trial 3 of 15" during sessions
3. **Auto-advance** — after a clip ends, blank screen for 2 s, then load next
4. **Per-trial reaction window** — only count brake presses within `[event_start_ms - 1000, event_start_ms + 3000]` as "correct"
5. **Keyboard shortcuts** — SPACE = brake, ESC = pause, ENTER = next, F11 = fullscreen

These map to changes in `src/ui/main_window.py` and `src/core/data_logger.py`.
